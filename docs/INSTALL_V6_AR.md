# KMSA v6 — تحديث إدارة الدورات والدفعات (إصدار تجريبي متوافق مع v5.9)

## قبل البدء
**هذه حزمة تحديث فوق v5.9، وليست نسخة مستقلة من المشروع.** لا تغيّر أي شيء في الإنتاج قبل اختبار التحديث في Supabase تجريبي وGitHub Actions.

احتفظ بنسخة كاملة من كود v5.9، ونسخة احتياطية من Supabase Auth + قاعدة البيانات قبل أي تشغيل. يجب إتمام ترقيات 0017 و0018 مسبقًا. إذا واجهت خطأ `relation public.cycle_batches does not exist` فقاعدة البيانات غير جاهزة لـv6.

## التركيب — بالترتيب
1. فك ضغط حزمة `KMSA_v6_ADMIN_UPDATE.zip` **في جذر مشروع v5.9**، مع الحفاظ على المسارات.
2. افتح PowerShell داخل جذر المشروع، وشغّل:

```powershell
node scripts/apply_v6_admin.mjs
cd apps\web
npm.cmd ci
npm.cmd run build
cd ..\..
node scripts/v6-static-check.mjs
```

3. إذا أعطت أداة الدمج رسالة «لا تطابق v5.9»، **توقف**. لن تغيّر الأداة أي ملف. لا تحاول مطابقة الكود يدويًا دون مراجعة النسخة المثبتة.
4. على قاعدة **Supabase تجريبية** مكتملة v5.9، نفّذ `supabase/migrations/0019_v6_admin_safety.sql` مرة واحدة من SQL Editor **أو** عبر migrations، وليس الاثنين معًا.
5. انشر Edge function `workflow` من النسخة بعد التعديل، ثم انشر الواجهة.
6. بعد اختبار الحالات أدناه، جهّز ترقية الإنتاج وصيانة قصيرة. تشغيل SQL قبل نشر الواجهة القديمة قد يوقف زر اعتماد الدورة القديم مؤقتًا وهذا مقصود أمنيًا.

```powershell
npx.cmd supabase@latest functions deploy workflow --use-api
git add .
git commit -m "KMSA v6 safer cycles and administration UX"
git push origin main
```

## أين أجد الإضافات؟
- **الدورات ← افتح دورة ← الدورة المعتمدة لمساحة العمل:** بطاقة مستقلة، فحص قبل الاعتماد، تأكيد بكتابة رمز الدورة، وعرض آخر الانتقالات وزر الرجوع للدورة السابقة مباشرة بعد آخر تحويل.
- **الدفعات ← افتح دفعة ← استيراد CSV:** تظهر **جميع** الأسماء بصفحات للعرض، مع بحث وتحديد فردي وتحديد كل الجاهزين. تتحقق قاعدة البيانات من الرقم الجامعي والبريد قبل السماح بالاستيراد. اختيار من سيُستورد لا يحدث تلقائيًا.
- **الدفعات ← أفراد الدفعة:** زر إضافة عضو فرديًا.
- **الحسابات:** اسم + رقم جامعي + دفعة + بريد عند ظهور الشخص (بحسب مواضع العرض المدعومة).
- **العمليات الحساسة:** نوافذ تأكيد من داخل الموقع، وإزالة إمكان استخدام وظيفة الاعتماد القديمة وإعادة كلمة مرور مدير آخر بواسطة النموذج العادي.

## ضمان عدم فقدان البيانات عند تغيير الدورة
- كل دورة تبقى محتفظة بمشاريعها ومقترحاتها وتكليفاتها وسجلاتها.
- التغيير يعيد تحديد الدورة الحالية وصلاحيات مناصبها فقط.
- **الرجوع**: بعد انتقال بالخطأ، افتح الدورة السابقة، واضغط «الرجوع إلى هذه الدورة السابقة»، ثم اكتب رمزها وأكّد. يعمل هذا إذا كان **الانتقال السابق هو آخر انتقال مسجل**. إذا وقع أكثر من انتقال متتالٍ، يستلزم المرور عبر أحدث دورة وسجلها بالترتيب، دون حذف أعمال أي دورة.
- حتى إذا بدأ عمل في الدورة الجديدة، لا يحذف الرجوع العمل؛ يبقى متعلقًا بتلك الدورة، ويُعرض تحذير بذلك.
- النسخة السابقة من الدالة القديمة `activate_kmsa_cycle` تصبح غير قابلة للتنفيذ من المستخدم العادي، ومسار `ADMIN_CYCLE_ACTIVATE` القديم يُعطّل في وظيفة workflow لمنع تجاوز مراجعة v6.

## اختبارات قبول قبل النشر
1. إدخال دورة جاهزة وإجراء preview؛ يجب أن تظهر أعداد المشاريع والمقترحات الحالية والجديدة.
2. التأكيد دون كتابة رمز الدورة يجب ألا يسمح بالحفظ.
3. تغيير الدورة في نافذتين: الثانية يجب أن تفشل بخطأ `CYCLE_CHANGED_RELOAD`.
4. الرجوع للدورة السابقة بعد اعتماد دورة خطأ؛ يظل عدد مشاريع كل دورة وسجلاتها ثابتًا.
5. تشغيل العملية مرتين لا يفعّلها مرتين.
6. رفع CSV به أرقام جامعية متكررة في الدفعة نفسها ودفعتين مختلفتين؛ يجب إيقاف السجلات المتعارضة.
7. تحديد 3 أسماء فقط من 50؛ يجب ألا تُنشأ إلا حسابات الأسماء الثلاثة.
8. إضافة عضو واحد، ثم تجربة إعادة إضافته بنفس الرقم؛ يجب منع التكرار.
9. تغيير شاغل سكرتارية في دورة نشطة؛ تُسجل العملية وتنتقل صلاحيات المنصب دون نقل ملكية المشاريع.
10. محاولة إعادة تعيين كلمة مرور مدير آخر من حساب المدير؛ يجب رفضها.

## حدود ما تم التحقق منه
- فحص ملفات TypeScript الجديدة مقابل تبعيات ZIP المرفق أظهر عدم وجود أخطاء في **المكونات الجديدة**؛ ولكن النسخة القديمة المستخدمة لاجتياز هذا الفحص تحتوي أصلًا على أخطاء TypeScript أخرى.
- لم يتوفر ZIP الكامل لـv5.9 لاسترجاع بايتاته ضمن بيئة التنفيذ، ولذلك لم يمكن **اختبار تطبيق الدمج أو البناء النهائي عليه**. آلية الدمج تتوقف دون تعديل عند اختلاف العلامات المتوقعة.
- لم تُجرَ تجربة PostgreSQL حقيقية أو نشر Supabase فعلي. لا يمكن اعتبار الترقيات معتمدة للإنتاج حتى إجراء التجارب المذكورة.
- لا تحل الحزمة جميع مشكلات الإدارة غير المتعلقة بالدورات والدفعات، ولا تُعد تنفيذًا كاملًا لنطاق v6 الذي صيغ سابقًا. تتطلب هذه البنود استكمالًا بعد اختبار الدمج الفعلي.
