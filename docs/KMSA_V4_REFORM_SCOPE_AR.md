# نطاق الإصلاح في KMSA Operating System v4

## ما الذي يحاول النظام إصلاحه؟

النظام هو نظام متابعة وتنفيذ ومساءلة. لا يهمه إن كان المشروع تابعًا لمكتب أو لجنة أو فريق؛ المهم أن يعرف:

`النتيجة → المسؤول → التقدم الفعلي → الخطر المبكر → تدخل السكرتير → الدليل → التعلم المؤسسي`

## ما الذي تعمدنا عدم بنائه؟

- لا يوجد Organogram تفصيلي للرابطة داخل النظام.
- لا نحول كل مكتب أو لجنة مكتوبة في لائحة إلى كيان تقني.
- لا ننشئ Role تقنيًا لكل منصب.
- لا نجبر المهمة الصغيرة على المرور بمشروع ومحطات إنجاز.
- لا نكرر تقريرًا أسبوعيًا يدويًا إذا كانت بيانات العمل موجودة أصلًا.

## لماذا توجد «المناصب/صفات العمل» إذن؟

توجد فقط عندما تؤثر مباشرة في المتابعة.

مثال: إذا كان كل أمين أكاديمي يرفع تقريرًا دوريًا ويحضر اجتماعًا مشتركًا، نسجل «أمين أكاديمي» كصفة عمل. عند إسنادها لستة أشخاص، يولد النظام التزامًا مستقلًا لكل واحد وقائمة حضور مستقلة، دون بناء مجلس أو مكتب أو شجرة تنظيمية كاملة.

الدورية قابلة للتغيير. تغييرها اليوم يؤثر على الاستحقاقات المستقبلية ولا يمحو التقارير السابقة.

## أربعة مسارات عمل فقط

1. **المشاريع:** عمل ممتد له نتيجة واضحة ومحطات إنجاز وتحديث دوري.
2. **المهام السريعة:** «افعل X قبل Y» دون تعقيد مشروع.
3. **العمل الدوري:** التزام يتكرر ويحتاج مخرجًا أو تقريرًا.
4. **المقترحات:** طلب يدخل مسار مراجعة وقرار ونسخ موثقة.

الاجتماع الدوري أداة جماعية مرتبطة بالعمل الدوري، مع حضور ومخرجات، وليس Module إداريًا ضخمًا.

## قاعدة قبول أي Feature جديدة

لا تدخل ميزة جديدة إلا إذا أجابت بنعم على أحد الأسئلة:

- هل تجعل المسؤولية أوضح؟
- هل تكشف التعثر أبكر؟
- هل تقلل اعتماد العمل على الذاكرة والرسائل الخاصة؟
- هل تجعل تدخل السكرتير أو رقابة GS قابلة للرؤية؟
- هل تحفظ دليلًا أو تاريخًا نحتاجه لاحقًا؟

إذا كانت مجرد إدخال بيانات إضافي، تُرفض.
