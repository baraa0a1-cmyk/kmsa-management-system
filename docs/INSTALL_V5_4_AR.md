# KMSA v5.4 — مشروع بجدول واضح ومراجعتين مستقلتين

## الأساس
التحديث موجّه إلى **KMSA v5.3**. إنه تعديل على تجربة المشاريع، وليس نظامًا جديدًا للهيكلة أو تحويل المحادثات من تيليجرام. يستخدم جداول Supabase وسجلات v5.3 القائمة؛ **لا يوجد ملف ترقية SQL جديد في v5.4**.

## تغييرات أساسية
- حالات المحطات الثلاث في واجهة المشروع: **جارٍ العمل، اكتمل، تعثر**. حالات قديمة مثل «لم يبدأ» تظهر ضمن «جارٍ العمل» في العرض الجديد فقط، دون تغيير سجلاتها القديمة في قاعدة البيانات؛ لا تعني الحالة أن تقدمًا وقع بالفعل.
- أنواع آخر ما حدث: **تقدم جديد، لا يوجد تقدم، عائق / تأخر، طلب تغيير الموعد**. الأخير يفتح نافذة طلب موعد مستقل، لا يرسل تحديث إنجاز.
- **تقييم التحديث** منفصل عن **تقييم النتيجة**. الأخير يظهر فقط عندما يقول المسؤول إن المحطة اكتملت. كلاهما يرتبط بالنسخة التي راجعها المشرف، ولا يوقفان سير العمل.
- ملاحظات المشرف، ومنها سبب «يحتاج متابعة» أو «تحتاج تعديلًا»، تُعرض للمسؤول مباشرة.
- زر ⓘ يوضح توقيت آخر تحديث، ويتيح فتح سجل المحطة. زر أعلى المشروع يعرض سجل المشروع كله.
- طلب تغيير الموعد يقدمه المسؤول مع السبب ويقرره المشرف من الجدول نفسه. يُحتفظ بالموعد الأصلي وقرار المراجعة.
- طلب تحديث من المسؤول أصبح نافذة واضحة؛ وعند نجاحه يظهر إشعار للمسؤول. عند تعذر إيصال الإشعار يظهر تحذير ولا يوهم المشرف بأن التبليغ نجح.
- إصلاح مهم: كان قارئ الإشعارات يستدعي اسم RPC غير الموجود `notification_feed` بدل `user_notification_feed` المعرّفة في الترقية القديمة. أصبح يعرض الأخطاء ويُحدّث القائمة دوريًا.
- إزالة «تأخر التقرير الدوري» من أسباب الإنذار في لوحة البداية للمشاريع؛ يُعتمد على تأخر المحطة والعوائق لا على تقرير لم نعد نلزمه.
- واجهة أخف وأنظف، مع جدول مضغوط قابل للتمرير داخليًا واسم المحطة مثبت، ونوافذ داخل الموقع، ومؤشرات حفظ واضحة.

## التثبيت على Windows PowerShell
1. احتفظ بنسخة احتياطية لمجلد المشروع، وافتح `KMSA_v5_4_UPDATE.zip` وانسخ محتوياته **مع الحفاظ على المسارات** فوق المشروع v5.3.
2. افتح PowerShell **من جذر المشروع**:

```powershell
cd "C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2"
cd apps\web
npm.cmd ci
npm.cmd run build
```

لا تنتقل للرفع إن فشل البناء. لا تغير Execution Policy؛ `npm.cmd` يعمل في PowerShell على Windows.

3. انشر وظيفة Supabase **workflow** لأنها تعدلت، بما فيها الاعتماد على `_shared/common.ts`. لا يلزم إعادة نشر Google Apps Script أو `document-job` لهذا التحديث:

```powershell
cd ..\..
npx.cmd supabase@latest functions deploy workflow --use-api
```

4. **بعد نجاح البناء والنشر**، ارفع تغييرات الواجهة وملفات الاختبارات إلى GitHub:

```powershell
git add .
git commit -m "KMSA v5.4 compact projects and review UX"
git push origin main
```

5. تحقق من GitHub Actions: النجاح يعني بناء الواجهة والتحقق الثابت فقط، وليس ضمان صحة اتصال Supabase أو الإشعارات أو Cron.

## اختبارات قبول حيّة قبل الاعتماد
1. حساب مسؤول مشروع: غيّر محطة إلى **جارٍ العمل** ثم سجّل «تقدم جديد». تحقق من ظهور حالة الحفظ ثم التحديث والسجل.
2. حساب مسؤول: سجّل **لا يوجد تقدم**؛ تأكد أن تاريخ آخر تحديث تغير لكن لا تُحسب إفادة جديدة كتقدم فعلي في مؤشرات التذكير.
3. حساب مسؤول: اختر **اكتمل** دون نتيجة، تأكد من رفض الحفظ. اكتب وصفًا محددًا للنتيجة ثم احفظ.
4. حساب مشرف: قيّم آخر تحديث «مناسب» أو «يحتاج متابعة». تحقق أن التقييم يخص **التحديث**، وليس النتيجة.
5. بعد الاكتمال، قيّم **النتيجة** «النتيجة مناسبة» أو «تحتاج تعديلًا»، وتحقق من ظهور الملاحظة لدى المسؤول.
6. بعد تعديل المسؤول للنتيجة، لا تُعد المراجعة القديمة مراجعةً للنسخة الجديدة.
7. انقر ⓘ ثم افتح سجل المحطة. افتح زر **سجل المشروع الكامل** وتأكّد من ظهور التقييمات والمواعيد والتحديثات.
8. حساب مسؤول: اطلب تغيير الموعد. حساب مشرف: افتح «مراجعة طلب الموعد» في الخلية ووافق/ارفض، وتحقق من ظهور القرار في السجل.
9. حساب مشرف: «طلب تحديث» مع توضيح؛ تحقق من وصول إشعار إلى **حساب المسؤول**، وعدم قبول الطلب الثاني ما دام الأول مفتوحًا.
10. تحقق من قائمة الإشعارات: وصول إشعار عند مراجعة إيجابية أو سلبية، وقراءة الإشعار، وتجدد القائمة عند إعادة فتح التبويب.
11. حساب نائب هو مسؤول المشروع: لا يراجع عمله بنفسه. حساب السكرتير الذي ينفذ مشروعًا: يستفيد من استثناء المراجعة الذاتية الذي اعتمدتموه.
12. اختبر شاشة 1366px وهاتف: ظهور الحالة كاملة بوضوح، وثبات المحطة عند التمرير الأفقي، وإمكانية التحديث دون الوصول إلى أسفل الصفحة.

## حدود الفحص
نجحت اختبارات TypeScript والاختبارات البرمجية الثابتة محليًا. لم يكتمل `vite build` داخل بيئة Linux الخاصة بإعداد الحزمة، لأن `node_modules` المستورد يتضمن ملفات Rollup/Esbuild الخاصة بـWindows. بناء GitHub Actions بـ `npm ci` سيستخدم حزم Linux المناسبة. لم تُنفذ اختبارات قاعدة بيانات أو صلاحيات أو Telegram أو Cron حيّة في هذه البيئة.

في حال لم تصل الإشعارات رغم تحديث الموقع: تأكد من نشر وظيفة `workflow`، ووجود `user_notification_feed`، ومن تنفيذ ترقيات قاعدة البيانات السابقة بما فيها `0010_operating_system_v4.sql` بسياسة `user_notifications_read`، ومن تشغيل `scheduled-monitor` للتذكيرات الآلية.
