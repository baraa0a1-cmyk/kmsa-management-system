# تثبيت KMSA v5.9 — دليل عملي

## قبل البدء
1. يجب أن تكون النسخة الحالية **v5.8**، وترقية `0017_cycle_identity_import_v5_8.sql` قد نُفذت بالفعل.
2. خذ نسخة احتياطية من قاعدة البيانات. احتفظ بإصدار v5.8 للرجوع إليه إذا ظهرت مشكلة.
3. **لا تبدأ على قاعدة البيانات الحية التي تضم مئات الطلاب.** جرّب أولًا في Supabase تجريبي مع حساب مدير وحسابين لطالبين.

## الترتيب الصحيح
1. في SQL Editor نفّذ `KMSA_V5_9_UPGRADE.sql` مرة واحدة، **أو** نفّذ migration `0018_admin_batches_and_cycles_v5_9.sql` عبر migrations. الملفان متطابقان؛ لا تشغّلهما معًا.
2. فك `KMSA_v5_9_UPDATE.zip` فوق مشروع v5.8 مع استبدال الملفات المتطابقة.
3. انشر وظيفة الخادم المحدثة:

```powershell
cd "C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2"
npx.cmd supabase@latest functions deploy workflow --use-api
```

4. نفّذ فحص الواجهة:

```powershell
cd apps\web
npm.cmd ci
npm.cmd run build
cd ..\..
```

5. بعد نجاح البناء والفحوصات، ارفع التعديلات إلى GitHub:

```powershell
git add .
git commit -m "KMSA v5.9 independent admin and batches"
git push origin main
```

## سيناريو اختبار القبول
- الدخول بحساب ADMIN ينقلك إلى `workspace/admin` مباشرة ولا تظهر السكرتارية العامة أو بوابة العضو.
- إنشاء «الدفعة 102» بدون اختيار دورة، ثم إضافة مستوى وتعديله بعد الحفظ.
- استيراد CSV صغير (عضوان تجريبيان) بكلمة أولية موحدة من 12 حرفًا على الأقل؛ يتطلب الدخول الأول تغييرها.
- إعادة استيراد CSV نفسه تعيد `EXISTS` ولا تغيّر كلمات المرور.
- نقل عضو إلى دفعة أخرى دون سبب؛ ثم التحقق من سجل `kmsa_batch_transfers` وبقاء الحساب نفسه.
- إنشاء دورة `KMSA29` باسم «دورة 2029-2030» دون دفعات أو تواريخ؛ فتحها، إضافة دفعات تم إنشاؤها سابقًا، اختيار شاغلي المقاعد ثم تفعيلها.
- يجب ألا يغير مجرد فتح الدورة الجديدة الدورة الحالية. تغيير اسم دورة نشطة يجب أن يُحدّث `cycles` و`system_settings` في العملية نفسها.
- مقعد مساعد السكرتير العام موجود، لكنه لا يمنح صاحبه جميع صلاحيات `GS` تلقائيًا.
- تجربة الوصول لعملية `ADMIN_BATCH_MEMBER_MOVE` بحساب عادي: يجب رفضها من قاعدة البيانات حتى عند إرسال الطلب يدويًا.
- محاولة الدخول إلى مسارات `/` أو `/workspace/projects` كمدير نظام: يجب تحويلك إلى إدارة النظام.
- التحقق من إمكانية تغيير كلمة مرور المدير بنفسه.

## تنبيهات أمنية مهمة
- كلمة المرور الأولية **مشتركة** بناءً على طلب الرابطة. إن نشرت في قناة تيليجرام يعرفها كل المشاركين فمن الممكن أن يستعملها أي شخص يعرف بريد طالب آخر **قبل تغيير الطالب لكلمته**. لا تنشر قائمة حسابات الدخول في الرسالة نفسها، وحدد وقتًا قصيرًا لإنشاء الحسابات وتغييرها. الأفضل أمنيًا كلمات أولية فردية، لكن التحديث يحترم خيار الكلمة الموحدة.
- لا يمكن لمدير النظام معرفة كلمة المرور الجديدة التي يختارها العضو. عند النسيان يستبدلها بكلمة مؤقتة جديدة.
- لم يتم اختبار قاعدة Supabase الحية، ولا توليد نسخة إنتاج Vite محليًا في البيئة الحالية بسبب اعتماد native Rollup الخاص بWindows. اعتمد نجاح GitHub Actions والاختبار التجريبي قبل الانتقال للإنتاج.

## تغييرات مستقبلية غير مشمولة
- إغلاق بقية أعطال المشاريع السابقة، ونقل القيادات أثناء الدورة الفعالة بإجراءات رسمية، ومراجعة كل سياسات RLS على قاعدة اختبار كاملة.
