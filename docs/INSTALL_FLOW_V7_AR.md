# KMSA Flow 7.0 — تثبيت المرحلة الجديدة لمتابعة المشاريع

## مهم قبل أي إجراء

هذه الحزمة **إضافة غير هدّامة** إلى ملفات مشروعك القائم، وليست استبدالًا كاملًا له. تحتفظ بمحطات الإنجاز، والمشاريع، والقرارات، وسجل البيانات القديم. تعرض المسارات الجديدة واجهات حديثة، وتترك مسارات الأدوات القديمة تحت `/classic`.

**حد التحقق:** بنيت الحزمة على الملفات المصدرية التي أمكن الوصول إليها في هذه الجلسة (نسخة v6.4 المرفوعة)، وفحصت TypeScript و33 اختبارًا آليًا على هذا المصدر. **لم تتوفر لديّ نسخة v6.6 الكاملة المثبتة لديك، ولم أجرب Supabase الحي**. لذلك لا تعتبر الحزمة جاهزة للنشر العام قبل تجربتها على فرع Git تجريبي، مع نسخة احتياطية من قاعدة البيانات. وبالأخص: منطق `scheduled-monitor` في v6.5/v6.6 قد يواصل إرسال تنبيهات المتابعة السابقة، بينما الواجهة الجديدة تعرض سجلات تحقق v7؛ يجب توحيدها قبل اعتمادها نهائيًا على المستخدمين. لا أطلب منك إعادة ربط Supabase.

## التغييرات

- عرض 3 تبويبات فقط: **سير المشاريع / متابعة الإشراف / قرارات المشاريع**.
- مشروع واحد في متابعة الإشراف، مع عرض المستجد والإجراء المطلوب والاسم المكلف.
- تحديث واحد من مسؤول التنفيذ يشمل حتى 8 محطات يجري العمل عليها بالتوازي، مع الحفاظ على معايير كل محطة وتقييم نتيجتها على حدة.
- تحقق إشرافي واحد بالمشروع بدل نموذج منفصل لتقييم المستجد وإعادة إدخاله في تحقق آخر. التواصل يتم عبر تيليجرام، والتسجيل في KMSA للواقع الذي جرى التحقق منه.
- مشكلة تستدعي معالجة: تسجيل واحد للمطلوب والمسؤول والموعد؛ لا حاجة لتوثيق كل محادثة.
- تمييز **تأخر التوثيق** عن **عدم تنفيذ العمل**؛ لا يعد أحدهما إثباتًا للآخر.
- تدخل السكرتير يظهر مستقلًا عن تحقق المشرف المفوض؛ عدم متابعة السكرتير محسوب وفق مهلة مراجعة واضحة.
- شريط ملخص، حالات مختلفة الألوان، إجراءات رئيسية ظاهرة، تقويم من الموقع، دعم الأجهزة الصغيرة.
- إغلاق المشروع بنجاح يتطلب تقييم النتيجة النهائية للمحطات المعتمدة، ولا يغلق تلقائيًا بمجرد تغيير حالات المحطات.

## 1. التحضير

1. احتفظ بنسخة احتياطية من قاعدة Supabase ومن مجلد Git قبل تثبيت أي شيء.
2. **أنشئ فرعًا تجريبيًا** في مشروع Git. افتح PowerShell داخل مجلد المشروع وشغّل:

```powershell
$Project = 'C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2'
Set-Location $Project
git status
git switch -c feature/kmsa-flow-v7
```

إذا لم يكن المشروع في المسار المذكور، غيّر قيمة `$Project` إلى المسار الحقيقي على جهازك.

## 2. فك حزمة التحديث إلى جذر المشروع

ضع الملف `KMSA_Flow_v7_Update.zip` في Downloads، ثم شغّل:

```powershell
$Zip = Join-Path $env:USERPROFILE 'Downloads\KMSA_Flow_v7_Update.zip'
Expand-Archive -LiteralPath $Zip -DestinationPath $Project -Force
Set-Location $Project
node scripts/install-flow-v7.mjs --check
```

إذا أعطى الفحص أن المسارات غير متطابقة، **توقف ولا تُجبر السكربت على الاستبدال**؛ ستكون محتاجًا إلى دمج نسختك الفعلية من App.tsx. هذا إجراء حماية مهم لأن النسخة v6.6 المثبتة لديك لم تكن مرفقة هنا.

## 3. قاعدة البيانات — على Supabase تجريبي أولًا

شغّل محتوى `supabase/migrations/0026_project_flow_v7.sql` من SQL Editor على قاعدة بيانات **تجريبية** بعد تثبيت migrations السابقة، وتأكد من نجاح العملية كاملة قبل الانتقال. لا تكرر تشغيل الملف بعد نجاحه. هذا الملف يضيف جداول مستقلة فقط، ولا يحذف محطات الإنجاز أو المشاريع أو السجل التاريخي.

**مهم:** يوجد trigger جديد يمنع اعتماد إغلاق المشروع بنجاح دون تقييم نتائج المحطات. اختبر أولًا مشاريعك التاريخية وحالات الإغلاق؛ إن كان هناك تعارض لا تعممه على الإنتاج قبل مراجعته.

## 4. تفعيل الواجهات واختبار البناء

```powershell
Set-Location $Project
node scripts/install-flow-v7.mjs --activate
Push-Location apps\web
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'فشل البناء — توقف قبل النشر' }
Pop-Location
node scripts/check-flow-v7.mjs
if ($LASTEXITCODE -ne 0) { throw 'فشل اختبار Flow v7' }
```

إذا لم تكن حزمة node_modules موجودة، شغّل `npm.cmd ci` داخل `apps\web` قبل البناء.

## 5. نشر الوظيفة الجديدة إلى Supabase التجريبي

```powershell
Set-Location $Project
npx.cmd supabase@latest functions deploy project-flow --use-api
if ($LASTEXITCODE -ne 0) { throw 'فشل نشر project-flow' }
```

لا يتطلب ذلك إعادة تسجيل دخول أو Project Ref طالما الاتصال السابق صالح. **تحقق أن الربط يتجه إلى مشروع Supabase التجريبي** قبل نشر الوظيفة. لا تنشرها على قاعدة الإنتاج أثناء التجريب.

## 6. رفع فرع التجربة إلى GitHub (أوامر كاملة)

```powershell
Set-Location $Project
git add apps/web/src/App.tsx
git add apps/web/src/features/project-flow/
git add supabase/functions/project-flow/index.ts
git add supabase/migrations/0026_project_flow_v7.sql
git add scripts/install-flow-v7.mjs scripts/check-flow-v7.mjs
git add docs/INSTALL_FLOW_V7_AR.md FLOW_V7_CHANGELOG_AR.md
git diff --cached --stat
git commit -m 'KMSA Flow v7 - simplified project tracking and supervision'
git push -u origin feature/kmsa-flow-v7
```

إذا نجحت التجربة وافق على دمج الفرع عن طريق GitHub Pull Request بعد اختبار صلاحيات ثلاثة حسابات حقيقية ومسار الإغلاق.

## 7. اختبار المتابعة الواقعي

- مسؤول التنفيذ يرفع تحديثًا يشمل محطتين في عملية واحدة؛ تظهر كلتا المحطتين دون فقد تاريخهما.
- المشرف المفوض يسجل نتيجة تحقق واحدة بناءً على تواصله في تيليجرام، ولا يحتاج لإعادة تقييم التحديث نفسه بنموذج آخر.
- اكتشاف تعثر يفتح مشكلة متابعة واحدة؛ مراجعة المسؤول ثم التحقق من حلها، وإغلاقها من المشرف.
- السكرتير يرى تأخر المشرف، ولا تُحسب متابعته الشخصية متابعةً قام بها النائب.
- السكرتير يفتح قرارات المشروع ويستخدم الإغلاق والتأجيل عبر المسار القديم الآمن.
- المسؤول يعلن اكتمال محطة؛ لا تُعتمد نتيجتها قبل تقييم مستقل، ولا يُغلق المشروع تلقائيًا.
- يختبر المستخدمون الصلاحيات من حساب مسؤول وحساب مفوض وحساب سكرتير، لا من حساب مدير النظام وحده.

## 8. العودة إلى الواجهة القديمة إذا لم تنجح التجربة

```powershell
Set-Location $Project
node scripts/install-flow-v7.mjs --restore
```

يعيد هذا ملفات التوجيه إلى المسارات القديمة بناءً على النسخة الاحتياطية المحلية، دون حذف البيانات. **لا يزيل جداول قاعدة البيانات الجديدة**، ولذلك يفضل التجربة أولًا على نسخة Supabase منفصلة.

## نقاط مفتوحة قبل إعلان الإنتاج

1. توحيد تنبيهات/جدولة v6.5 مع تحقق Flow v7، منعًا لازدواج الإنذارات.
2. مواءمة نسخة App.tsx وملفات الواجهات مع **النسخة v6.6 الفعلية** التي تعمل لديك (إذا فشل `--check`).
3. اختبار التحديث والإغلاق والتأجيل وتغيير التكليف على قاعدة Supabase تجريبية.
4. اختبار أن المحطة التي أُعلن اكتمالها لا يمكن إغلاق مشروعها دون مراجعة نتيجتها.
