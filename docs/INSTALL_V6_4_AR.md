# KMSA v6.4 — تحديث متابعة المشاريع والإشراف

> التحديث مبني فوق **v6.3**. يشمل قاعدة البيانات والواجهة ووظيفة Supabase `workflow`. لا يغير نموذج إنشاء المشاريع، ولا يدمج «سير المشاريع» و«متابعة الإشراف» و«قرارات المشاريع».

## ما الذي تغير؟

- **جدول إفادات للمحطات الجارية:** 8 ساعات للمحطة القريبة جدًا، يوم تقريبًا للمحطات حتى ثلاثة أيام، يومان للمتوسطة، ثلاثة أيام للأطول. يُنشأ تلقائيًا بعد بدء المشروع، ولا يُنشأ بأثر رجعي موعد إفادة فائت عند ترقية مشروع موجود.
- **الالتزام لا يُعاد ضبطه بكتابة تحديث مبكر**: الإفادة تبقى مرتبطة بموعد تحقق محدد مثبت في قاعدة البيانات.
- **إفادة واحدة بدل نموذجين دوري ومحطة:** أصبح تحديث المحطة هو التوثيق الرسمي؛ سجل الإفادات القديمة محفوظ. يجب أن يذكر المسؤول ما حدث والخطوة التالية؛ وإعلان الاكتمال يستلزم وصف النتيجة.
- **تقييم المتابع للمستجد بثلاث نتائج:** مناسب / غير كافٍ / غير واضح. الضعيف وغير الواضح يتطلبان ملاحظة وموعد تحقق من التصحيح. **تقييم النتيجة** مستقل عند اكتمال المحطة.
- **متابعة الإشراف:** «تحتاج تدخلك» / «تحت المتابعة» / «جميع المحطات»، مع مهلة تقييم متناسبة مع المحطة، وطلبين أقصاهما قبل تدخل السكرتير. الفشل في تقديم الإفادة منفصل عن تأخر المتابع في تقييمها.
- **صفحة المشروع:** المحطة الجارية وآخر الإفادة وتقييمها والخطوة القادمة، ثم جميع المحطات باختصار؛ التفاصيل والسجل القديم في جزء قابل للتوسيع.
- **قائمة المشاريع:** عرض أخف وبحث وفلاتر متقدمة مخفية افتراضيًا؛ العدادات مأخوذة من نفس البيانات التي تغذي صفحة الإشراف.
- **الصفحة الرئيسية:** إظهار الإجراءات المستحقة على السكرتير.

## قبل التثبيت

1. **خذ نسخة احتياطية حقيقية** من قاعدة بيانات Supabase ومن مجلد المشروع أو فرع Git الحالي.
2. اختبر أولًا على مشروع Supabase تجريبي يستعمل نفس ترحيلات v6.3، ثم تحقق من السيناريوهات أدناه قبل النشر الفعلي.
3. هذا الملف يحتوي على تعديلات تشمل قاعدة البيانات ووظيفة Edge Function؛ **رفع GitHub وحده لا يكفي**.
4. لا تعِد تنفيذ تحديثات SQL من v6.2 أو v6.3 ما دامت قاعدة البيانات الحالية تملكها.
5. التغيير يعطّل تقديم تحديث دوري مستقل عبر `PROJECT_UPDATE_ADD`. معلوماته التاريخية لا تُحذف. تأكد من نشر الواجهة ووظيفة `workflow` معًا بعد SQL.

## الخطوة 1 — SQL

من Supabase Dashboard → **SQL Editor** افتح **`KMSA_V6_4_UPGRADE.sql`** وشغّله على قاعدة تجريبية أولًا، ثم على الإنتاج بعد النسخ الاحتياطي. الملف نفسه موجود في `supabase/migrations/0023_milestone_followup_v6_4.sql`، ولا تحتاج تشغيل النسختين. ينشئ جدولًا وحقولًا جديدة ويضيف النوع `PROGRESS_UNCLEAR` إلى قيد التقييمات. لا يمسح بيانات المشاريع أو التقييمات القديمة.

تأكد من أن تنفيذ SQL انتهى بلا أخطاء. لا تنشر الواجهة الجديدة قبل تطبيق SQL؛ وإلا ستفشل قراءة مواعيد الإفادات.

## الخطوة 2 — نسخ ملفات التحديث في PowerShell

غيّر فقط مسار مشروعك إذا كان مختلفًا. تأكد من تنزيل الملف في `Downloads`:

```powershell
$Project = 'C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2'
$UpdateZip = Join-Path $env:USERPROFILE 'Downloads\KMSA_v6_4_FOLLOWUP_UPDATE.zip'

# احفظ نسخة محلية للرجوع إليها قبل الاستبدال
Copy-Item -LiteralPath $Project -Destination "${Project}_backup_before_v6_4" -Recurse

# فك التحديث داخل مجلد المشروع مباشرة
Expand-Archive -LiteralPath $UpdateZip -DestinationPath $Project -Force
Set-Location $Project
```

إذا نزّل المتصفح الملف إلى مكان آخر، عدّل `$UpdateZip` فقط. **لا تفك المشروع الكامل فوق نسخة Git بها تغييرات خاصة**؛ استخدم حزمة التحديث الصغيرة أعلاه.

## الخطوة 4 — نشر Supabase Edge Function

تحتاج إلى Supabase CLI وحساب له صلاحية النشر على المشروع. **غيّر `YOUR_PROJECT_REF` إلى Project Ref الفعلي من Supabase → Project Settings → General**. الأوامر:

```powershell
Set-Location 'C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2'

npx.cmd supabase@latest login
npx.cmd supabase@latest link --project-ref YOUR_PROJECT_REF
npx.cmd supabase@latest functions deploy workflow --use-api
```

لا تضع مفتاح `service_role` في الواجهة أو Git. إذا كان ملف `supabase/config.toml` يحتوي `project_id` placeholder، فإن الربط الصحيح يتم باستخدام أمر `link`.

## الخطوة 6 — اختبار تشغيلي لا غنى عنه

اختبر كل حالة بحسابات مختلفة: (أ) سكرتير (ب) نائب متابع مفوض (ج) مسؤول تنفيذ.

1. **محطة 3 أيام:** تأكد من إنشاء موعد إفادة مبكر، وتسجيل إفادة واحدة مع الخطوة التالية، وعدم تأخير الموعد لمجرد إرسال تحديث مبكر جدًا.
2. **غياب إفادة:** بعد انتهاء موعدها يظهر غياب الإفادة للسكرتير؛ لا يظهر أنه «لم يعمل» دون سند.
3. **المتابع المفوض:** يرسل المسؤول الإفادة؛ تظهر للمتابع للتقييم. إذا لم يقيّم خلال المهلة يظهر للسكرتير طلب التقييم؛ ثم الطلب الثاني وفق موعده؛ ثم التدخل.
4. **تقييم ضعيف / إفادة غير واضحة:** يضيف المتابع ملاحظة وموعد تحقق؛ يظهر التصحيح «تحت المتابعة»، وعند فوات الموعد دون إفادة أحدث يظهر «انتهى موعد التصحيح».
5. **تقييم النتيجة:** إعلان اكتمال المحطة يفتح تقييم النتيجة بشكل مستقل عن تقييم التقدم؛ تحقق من عدم تحويل التقدم المناسب إلى اكتمال تلقائي.
6. **عرض السكرتير:** تطابق عدد عناصر «تحتاج تدخلك» مع العداد الأحمر، وتطابق حالة المشروع بين القائمة والتفاصيل.
7. **مشروع مغلق ومحطة مستقبلية:** لا يظهران في عداد إفادات مستحقة لم تبدأ بعد.
8. **الصلاحيات والسجل:** المسؤول لا يستطيع تقييم نفسه خلاف الضوابط، ولا تختفي السجلات القديمة أو ملفات الأدلة.

## حدود التحقق في الحزمة

أُجري فحص TypeScript بنجاح، و39 فحصًا ثابتًا لـv6.4، و8 اختبارات محاكاة لمسار البيانات، واختبارات الإصدارات الإدارية السابقة. **لم يتم اختبار الاتصال مع Supabase الحية ولا الترحيل على قاعدة المستخدم ولا تنفيذ Vite build كاملًا داخل بيئة التطوير الحالية بسبب نقص حزمة Rollup المحلية**. يجب إجراء بناء Windows واختبار staging والاختبارات التشغيلية أعلاه قبل الاعتماد النهائي.

## الرجوع عند وجود مشكلة

- أبقِ نسخة SQL والنسخة الاحتياطية قبل الترقية. **لا تُسقط جدول المتابعة يدويًا لتتراجع**؛ فقد يكون قد حفظ سجلات متابعة جديدة.
- إذا ظهرت مشكلة واجهة: أرجع ملفات الواجهة ووظيفة `workflow` إلى commit سابق مع الاحتفاظ بنسخة DB، وراجع التوافق قبل إعادة النشر.
- إذا حدث خطأ بعد كتابة سجل: لا تكرر العملية تلقائيًا قبل التحقق من سجلات المشروع في Supabase؛ فقد تكون البيانات قد حُفظت وتعطلت الإشعارات فقط.
