# KMSA v5.6 — دليل تحديث دورة حياة المشاريع والتفويض

## الغرض
تحديث مركز فقط فوق **v5.5**: تبويب «سير المشاريع / متابعة الإشراف المفوض» داخل قسم المشاريع، بطاقة المحطة الأبرز، إدارة تكليف المنفذ والمتابع، وإجراء منفصل لإغلاق المشروع بنجاح أو إلغائه أو تأجيله، مع إجازة السكرتير وإمكانية استئناف المؤجل. لا يعود اكتمال كل المحطات إغلاقًا تلقائيًا للمشروع.

## قبل البدء
- احتفظ بنسخة احتياطية من ملفات المشروع ونسخة قاعدة البيانات Supabase. اختبر الترقية أولًا على مشروع تجريبي.
- يلزم أن تكون ترقيات v5 إلى v5.5 مطبقة سابقًا.
- لا تنسخ ملفات ZIP داخل `apps/web` مباشرة؛ يجب الحفاظ على هيكل المجلدات بدءًا من جذر المشروع.

## الترتيب الإلزامي

1. نفّذ **مرة واحدة** `KMSA_V5_6_UPGRADE.sql` في **Supabase SQL Editor** قبل نشر الواجهة أو وظائف Edge. ينشئ جداول `project_closure_requests` و`project_supervision_followups`، وحقول دورة حياة المشروع، ودوال معاملات نقل المسؤول وقرار الإغلاق. يتضمن RLS وقيود تنفيذ RPC لصلاحية `service_role` فقط.
   - بديلًا عن التنفيذ اليدوي، إذا كنت تدير كامل سجل migrations من أوله: استخدم ملف `supabase/migrations/0015_project_lifecycle_supervision_v5_6.sql` عبر `supabase db push`.
   - **لا تستخدم الطريقتين معًا للتحديث نفسه.**
2. فك `KMSA_v5_6_UPDATE.zip` فوق جذر مشروع **v5.5** مع الموافقة على استبدال الملفات.
3. افتح PowerShell في جذر المشروع وشغّل:

```powershell
npx.cmd supabase@latest functions deploy workflow --use-api
npx.cmd supabase@latest functions deploy scheduled-monitor --use-api
cd apps\web
npm.cmd ci
npm.cmd run build
```

4. **بعد نجاح البناء فقط**:

```powershell
cd ..\..
git add .
git commit -m "KMSA v5.6 project lifecycle and delegated supervision"
git push origin main
```

5. تحقّق من GitHub Actions ومن جدولة `scheduled-monitor` الفعلية. إذا كانت Cron غير مضبوطة، فلن تصل تنبيهات تجاوز متابعة النائب تلقائيًا.

## الصلاحيات
- **مسؤول التنفيذ**: يحرر تقدم المحطات؛ لا يستطيع إنهاء المشروع أو اعتماد نتيجة عمله بوصفه نائبًا.
- **المتابع المباشر المفوّض**: يراجع التحديثات ويطلب إغلاقًا أو إلغاءً أو تأجيلًا ويرفعه للسكرتير، ويجوز له نقل مسؤول التنفيذ عندما يكون مخولًا بمتابعة المشروع.
- **السكرتير**: وحده يغيّر المتابع المفوّض ويعتمد/يرفض مصير المشروع، ويسجّل إجراءات معالجة ضعف متابعة النائب. إذا كان هو المشرف المباشر، يقرر مصير المشروع في إجراء واحد موثّق.
- **GS**: يطلع على المشاريع وسجلاتها، دون إلزامه باعتماد إغلاق كل مشروع أو مراقبة النائب يوميًا.

## تجربة قبول فعلية — مطلوبة قبل الإطلاق
1. مشروع فيه محطتان: ضع كلتيهما «اكتمل»؛ تأكد أن المشروع **لا يغلق تلقائيًا**.
2. المتابع المفوّض يطلب **إغلاقًا بنجاح** مع وصف نتيجة واضحة؛ يجب أن يبقى طلبه معلقًا حتى قرار السكرتير.
3. السكرتير يرفض مع سبب؛ يظل المشروع جاريًا ويسجل السبب في التاريخ.
4. جرّب طلب نجاح جديد واعتماده؛ يتحول المشروع إلى **مغلق بنجاح**، ولا يقبل تحديث محطات أخرى.
5. مشروع ثانٍ: طلب **إلغاء** مع سبب، يعتمد السكرتير؛ يبقى المشروع وسجله محفوظين.
6. مشروع ثالث: طلب **تأجيل** مع موعد مراجعة مستقبلي؛ بعد الاعتماد يتوقف تحديثه التنفيذي، ثم يستطيع السكرتير استئنافه.
7. انقل مسؤول التنفيذ إلى عضو آخر بواسطة النائب المتابع، وافحص أن العضو الجديد يرى مساحة العمل والمحطات؛ لا يجوز أن يبقى للقديم إذن خاص فعّال.
8. حاول تكليف نفس النائب مسؤولًا ومتابعًا لمشروع واحد؛ يجب أن يمنع الخادم ذلك. ثم غيّر المشرف من حساب السكرتير فقط.
9. بعد تغيير النائب، لا يجوز عدّ تحديثات **قبل تاريخ تكليفه** فجوات في أدائه.
10. سجّل تحديثًا ومرّر نقطة مراجعة النائب التجريبية. يجب أن يظهر للسكرتير نقص المتابعة، ثم يستطيع تسجيل ما فعله وموعد فحص النتيجة. **لا يختفي نقص المتابعة لمجرد حفظ إجراء السكرتير.**
11. اختبر حساب GS والسكرتير والنائب والمنفذ منفصلة وتأكد من صلاحيات RLS.
12. اختبر تحويلًا فاشلًا (عضو غير فعّال) ورفض إغلاق فاشلًا؛ لا ينبغي أن تحدث تغييرات جزئية.

## حدود التحقق
فُحص المصدر ببرنامج TypeScript، واختبارات `scripts/v5-6-check.mjs` مع اختبارات الإصدارات السابقة. لم يُنفذ اختبار قاعدة بيانات حي أو مراجعة RLS فعلية. لا يكتمل بناء Vite المحلي في بيئة Linux الحالية لأن أرشيف المشروع يحتوي مكتبات Rollup لـWindows؛ يجب أن يجتاز بناء `npm.cmd run build` أو GitHub Actions قبل نشر الواجهة.

## ملاحظات تصميمية
- الواجهة تجمع سير المشاريع وإشراف السكرتارية كتبوبيْن داخل قسم «المشاريع»، دون قسم مستقل في القائمة الجانبية.
- بطاقة «المحطة الأبرز حاليًا» تظهر آخر تحديث وتاريخ المحطة أعلى الجدول؛ الجدول يبقى متاحًا كاملًا أسفلها.
- الإنهاء والإلغاء والتأجيل قرار مستقل عن حالات محطات الإنجاز، محفوظ في السجل مع الفاعل والتوقيت.
- فجوة مراجعة النائب تعني **عدم وجود مراجعة موثقة** لا حكمًا آليًا بإهماله. سجل الإجراء الإشرافي لا يغلقها إلا حين يصل تقييم فعلي.
