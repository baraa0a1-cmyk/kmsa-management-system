# تحديث متابعة المشاريع — KMSA v5.1

هذه **ترقية فوق v5 الحالية** وليست تغييرًا في الهيكلة أو نظام المقترحات أو مهام اللجان.

## ماذا سيلاحظ المستخدم؟

- صفحة المشروع: جدول محطات قصير؛ اضغط «التفاصيل» في أي صف لرؤية المخرج والسجل وروابط العمل ورفع ملف PDF أو صورة مباشرة.
- مسؤول المشروع: يحدّث حالة المحطة مباشرة؛ يسجل إفادة دورية قصيرة حتى إذا لم تتغير حالة أي محطة.
- مرجع العمل: رابط رسالة تيليجرام أو مستند HTTPS، دون اعتباره تعثرًا أو إثباتًا نهائيًا تلقائيًا.
- السكرتير: يطلع على إفادات المسؤول دون تعديلها؛ يمكنه إضافة ملاحظة عادية منفصلة أو تدخل موثق.
- GS: يقرأ السجل الأصلي وتوقيتات الأحداث؛ تظهر المخاطر المحسوبة من المواعيد والعوائق حتى لو كتب المسؤول «على المسار».
- العضو: يتجدد ظهور «مساحة العمل» بعد التكليف عند العودة للتبويب أو في غضون 45 ثانية طالما التبويب ظاهر.

## خطوات التثبيت

1. **نسخة احتياطية**: انسخ مشروع Git المحلي قبل ترقية الملفات.
2. فك `KMSA_Followup_v5_1_UPDATE.zip` في مجلد المشروع فوق الملفات الموجودة. **لا تستبدل `.env` أو الأسرار أو إعدادات الإنتاج.**
3. في Supabase > SQL Editor نفّذ **`KMSA_FOLLOWUP_V5_1_UPGRADE.sql`**. ينشئ جدولًا واحدًا فقط `project_activity_entries` لقراءة السجل التاريخي. لا يحذف أو يعدل بيانات المشاريع الحالية. يجب تثبيت ترقيات v5 السابقة أولًا.
4. انشر الوظيفة المعدلة فقط من جذر المشروع (في PowerShell):

   ```powershell
   npx.cmd supabase@latest functions deploy workflow --use-api
   npx.cmd supabase@latest functions deploy document-job --use-api
   ```

5. اختبر الكود ثم ادفع واجهة React إلى GitHub:

   ```powershell
   cd apps/web
   npm.cmd ci
   npm.cmd run build
   cd ../..
   git add .
   git commit -m "Improve v5 milestone follow-up"
   git push
   ```

   نفّذ `npm.cmd ci` على Windows في البيئة المحلية؛ مجلد `node_modules` غير مضمّن عمدًا في الحزمة.
6. بعد نجاح GitHub Actions، حدّث الموقع ثم اختبر سيناريوهات الاعتماد أدناه بحسابات مختلفة.

## اختبار قبول قبل تشغيل الفريق

1. مشروع بانتظار GS: لا تظهر أدوات تنفيذ للمسؤول؛ تجربة استدعاء الإجراءات مباشرة يجب أن تُرفض أيضًا.
2. بعد اعتماد GS، المسؤول يعدّل حالة محطة من الصف؛ يظهر حدث جديد بتاريخ ومؤلف مستقل لا يتغير بعد تعديل الحالة مجددًا.
3. مسؤول يضيف رابط رسالة تيليجرام؛ لا تتغير حالة المحطة، ولا تتحول إلى «متعثر».
4. مسؤول يكتب إفادة «لم يحدث تقدم لأننا ننتظر...» دون ضرورة إدخال الخطوة القادمة أو تغيير حالة المحطة؛ يستقبلها السكرتير وGS.
5. سكرتير يكتب «راجعوا التصميم» كملاحظة؛ لا يرتفع مستوى خطر المشروع تلقائيًا.
6. سكرتير يسجل تدخلًا فعليًا؛ يظهر إجراء منفصل بالوقت والاسم، ولا يمحو إفادة المسؤول.
7. مشروع له محطة متأخرة أو عائق مفتوح، مع عبارة مطمئنة في آخر تقرير: تبقى إشارة الخطر الآلية ظاهرة.
8. محطة جرى التحقق منها: المسؤول لا يستطيع إرجاعها «جارٍ العمل» بتحديث عادي.
9. عندما يكون السكرتير هو المسؤول عن محطة، لا يتحقق منها بنفسه؛ GS يستطيع التحقق بديلًا.
10. أضف مشروعًا أو مهمة لعضو عادي، ثم ارجع إلى نافذته؛ يظهر خيار مساحة العمل دون تسجيل دخول جديد.
11. ارفع PDF من صف المحطة مباشرة، وتحقق من أن حالته لا تصبح جاهزة للتحقق قبل نجاح حفظه في Drive.
12. تحقق من أن المشروع يفتح بسرعة ويعرض **سجل المشروع فقط**، ولا تظهر بيانات السكرتاريات الأخرى دون صلاحية.

**الانطلاق:** هذه فحوص لا بد من إكمالها في البيئة الحية. النجاح المحلي في TypeScript أو الفحص الساكن لا يكفي لإعلان الإطلاق.

## ملاحظات مهمة

- يظل العمل اليومي داخل تيليجرام؛ المنصة سجل متابعة لا Chat بديل.
- الرابط إلى مجموعة خاصة قد لا يستطيع GS فتحه؛ عند الحاجة إلى إثبات دائم، ارفع المستند الأصلي في صفحة المحطة.
- إدخالات سجل المشروع جديدة في هذا الإصدار؛ بيانات `project_updates` السابقة لا تُحذف وتظل متاحة، لكن السجل الموحد لن يحوّل التعديلات القديمة إلى أحداث مفصلة بأثر رجعي.
- يلزم نشر `document-job` أيضًا حتى يكون رفع الملف كمرجع منفصلًا عن طلب التحقق. لا يلزم تغيير Google Apps Script.
