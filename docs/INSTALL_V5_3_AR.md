# KMSA v5.3 — الجدول البسيط ومراجعة جودة النتائج وسجل المشروع

هذا التحديث يُطبّق فوق **v5.2**. ليس نظام هيكلة، ولا يضيف اعتمادًا إلزاميًا للانتقال بين المحطات.

## التغييرات

- جدول مشروع واحد بسبعة أعمدة: **المحطة، الموعد، الحالة، آخر ما حدث، النتيجة، الملاحظات، المتابعة**. القائمة المنسدلة للحالة مباشرة في الجدول، ويظهر نموذج داخلي فقط لإتمام التحديث.
- عند تحويل المحطة إلى **مكتمل** يُطلب وصف ما تحقق تحديدًا؛ لا يُقبل الإنجاز دون مخرج مكتوب.
- علامة **ⓘ** تعرض وقت آخر تحديث وصاحبه، وزرًا لفتح نافذة **سجل المحطة**. زر **سجل المشروع الكامل** أعلى بطاقة المشروع يفتح سجل جميع الأحداث المتاحة مرتبًا زمنيًا، من سجلات التنفيذ والتفويض والتصميم والمراجعات والأدلة والمواعيد.
- تقييم المتابع مرتبط **بالتحديث المحدد**: «مناسب / يحتاج متابعة» عند التقدم و«النتيجة مناسبة / تحتاج تعديلًا» عند الإنجاز. الاختيارات التي تحتاج متابعة تتطلب ملاحظة، وتصل للمسؤول. إن عدّل المسؤول التحديث لاحقًا تظهر النسخة الجديدة غير مراجعة.
- **استثناء السكرتير:** عندما يكون السكرتير نفسه مسؤولًا عن المشروع، يستطيع مراجعة عمله وفق طلبك. أما النائب أو العضو العادي فلا يراجع عمله، حتى إذا فُوِّض سابقًا للمتابعة؛ يراجعه السكرتير أو عضو مفوّض آخر مختلف عن المنفذ.
- النتيجة التي طُلب تعديلها تبقى في السجل ولا تُمحى، ويمكن للمسؤول إعادة إرسال وصف مصحح دون تعطيل المحطات الأخرى.
- زر تغيير الموعد الصغير بجوار الموعد يحتفظ بمسار v5.2: طلب مع تاريخ وساعة وسبب، موافقة المشرف، وحفظ الموعد الأصلي والتعديل في السجل.
- ملاحظات المتابع تُعرض مباشرة في عمود الملاحظات بعد حفظها.

## التثبيت

1. **نسخة احتياطية** من مشروعك ومن قاعدة Supabase.
2. فكّ `KMSA_v5_3_UPDATE.zip` فوق **مجلد الجذر** لمشروع v5.2 (الذي يحتوي `apps` و`supabase`). استبدل الملفات المتعارضة.
3. Supabase → SQL Editor → نفّذ `KMSA_V5_3_UPGRADE.sql` **مرة واحدة**. **بديل**: إذا كنت تستخدم migrations بواسطة `supabase db push`، اعتمد الملف `supabase/migrations/0014_project_quality_reviews_v5_3.sql` بدل SQL اليدوي، لا تنفذهما معًا.
4. انشر وظيفة `workflow` المعدلة فقط:

   ```powershell
   npx.cmd supabase@latest functions deploy workflow --use-api
   ```

5. من جذر المشروع (PowerShell):

   ```powershell
   cd apps\web
   npm ci
   npm run build
   cd ..\..
   git add .
   git commit -m "KMSA v5.3 project sheet and quality reviews"
   git push origin main
   ```

6. افتح **GitHub Actions** وتأكد من نجاح اختبارات v5 وv5.1 وv5.2 وv5.3 وبناء الواجهة قبل اعتماد النشر.

**لا يلزم تعديل** Google Apps Script أو وظيفة `scheduled-monitor` أو `document-job` في هذا التحديث.

## حالات اختبار حسابات حقيقية

1. **مسؤول مشروع عادي:** يغير حالة محطة مباشرة من السهم ويكتب النتيجة عند اختيار مكتمل؛ يستمر في المحطات الأخرى بلا اعتماد.
2. **متابع غير منفذ:** يختار «مناسب» أو «يحتاج متابعة»، ثم «النتيجة مناسبة» أو «تحتاج تعديلًا»، ويرى المسؤول الملاحظة، ويمكنه إرسال وصف النتيجة المصحح.
3. **مشروع ينفذه السكرتير:** يستطيع السكرتير مراجعة تحديثه ونتيجته.
4. **مشروع ينفذه نائب السكرتير:** لا يُسمح للنائب بمراجعة تحديثه، سواء من الواجهة أو عبر وظيفة الخادم. يمكن أن يتولى السكرتير أو نائب آخر مفوض المراجعة.
5. **سجل المحطة:** رمز ⓘ يعرض تاريخ التحديث، والسجل يعرض كل تحديث ومراجعته وتغيير الموعد.
6. **سجل المشروع:** يعرض الأحداث من كل المحطات والمراجعات والأدلة وقرارات تغيير المواعيد وتاريخ تفويض المتابع والتصميم بدءًا من تثبيت التحديث.
7. **تغيير الموعد:** يُطلب بسبب وتوقيت، ولا يتغير الموعد قبل قرار المشرف.
8. **صلاحيات GS:** يستطيع الاطلاع على السجل بناءً على صلاحيات القراءة القائمة دون مراقبة كل خطوة.

## حدود التحقق

- اجتاز المصدر فحص TypeScript، وفحوصات مصدر v5 وv5.1 وv5.2 وv5.3.
- **لم يكتمل تشغيل Vite محليًا على Linux**: حزم `node_modules` المتاحة في ZIP الأصلي خاصة بـWindows، وحزمة Rollup الأصلية لـLinux غير مثبتة. يلزم التثبيت النظيف (`npm ci`) وبناء GitHub Actions.
- لم يتم تشغيل اختبارات صلاحيات فعلية على Supabase الحي؛ اختبر المسارات بالأدوار المذكورة قبل اعتماد النسخة.
- لا يمكن للسجل إظهار محادثات تيليجرام أو وقائع سابقة لم تُسجّل. أحداث تغيير التصميم التي لم تكن تُكتب في سجل المشروع قبل v5.3 قد توجد في سجل التدقيق الإداري فقط.
