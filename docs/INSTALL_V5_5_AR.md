# تثبيت KMSA v5.5 — واجهة متابعة ومراجعات واضحة

تحديث موضعي **فوق v5.4**. ليس مشروعًا منفصلًا، ولا يضيف جداول أو SQL migrations جديدة.

## ماذا يعالج؟

- آخر تحديث من المسؤول يجعل تقييم التقدم السابق غير ساري للعرض الحالي؛ السجل القديم محفوظ.
- يظهر خيار «تقييم التحديث» للمشرف المفوض بمجرد وصول تحديث جديد للمحطة الجارية. عند اكتمال المحطة يكون تقييم النتيجة مستقلاً.
- عند الحفظ يتحقق الخادم من أن المشرف يقيّم التحديث الذي رآه، وليس تحديثًا سبقته إفادة أحدث.
- إبلاغ المشرف بتقدم جديد أو نتيجة جديدة مع اسم المشروع، المحطة، والإجراء المطلوب؛ وتعميق رابط الإشعار إلى المحطة المحددة.
- منع تكرار «طلب تحديث» إذا بقي طلب سابق بلا استجابة، وعرض «بانتظار رد المسؤول» بدلاً من زر ينتهي بخطأ.
- قائمة التنقل الجانبية مخفية افتراضيًا وتفتح بزر القائمة على الحاسوب والهاتف. شريط علوي يحمل شعار الرابطة ورابط بوابة العضو مرة واحدة.
- الصفحة الرئيسية تعرض الأعمال المطلوب اتخاذها وفق أقسام: المشاريع، المهام، المقترحات، العمل الدوري، مع إدراج تحديثات المشاريع المنتظرة للتقييم.
- صفحة جديدة للسكرتير: «إشراف السكرتارية»، تعرض المشاريع المفوضة للنائب، آخر تحديث، وهل راجع المتابع آخر نسخة منه.

## قبل التحديث

1. احتفظ بنسخة احتياطية من مجلد المشروع.
2. تأكد من وجود v5.4 وترقيات v5.2 وv5.3 في Supabase.
3. فك محتويات `KMSA_v5_5_UPDATE.zip` **في جذر المشروع نفسه**، مع استبدال الملفات.

## بناء Windows PowerShell

```powershell
cd "C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2\apps\web"
npm.cmd ci
npm.cmd run build
```

إذا ظهر خطأ في البناء **توقف ولا ترفع** الملفات إلى GitHub.

## نشر وظيفة الخلفية

```powershell
cd "C:\Users\baraa\Desktop\KMSA_Management_System_GitHub_v2"
npx.cmd supabase@latest functions deploy workflow --use-api
```

تعديل الخادم ضروري؛ مجرد رفع واجهة React لا يفعّل إشعارات التقدم أو حارس النسخ أثناء التقييم.

## رفع الموقع

```powershell
git add .
git commit -m "KMSA v5.5 supervision inbox and review UX"
git push origin main
```

تحقق من نجاح Build وDeploy في GitHub Actions. في حالات فشل وظيفة Supabase لا تعتبر النشر مكتملًا.

## اختبارات قبول حية يجب إجراؤها

1. مسؤول يُرسل تحديث تقدم جديد. يرى المتابع إشعارًا باسم المشروع والمحطة، ويظهر التحديث ضمن أعمال المشاريع بالرئيسية.
2. المتابع يقيّم «مناسب»، ثم يرسل المسؤول تحديثًا آخر. يظهر «تحديث جديد · لم يُقيّم» من دون حذف التقييم الأول من السجل.
3. افتح نافذة تقييم، ثم اطلب من المسؤول إرسال تحديث أحدث قبل الحفظ؛ يجب أن يرفض الخادم تقييم النسخة القديمة.
4. نائب مفوض يرى إشرافه المباشر، والسكرتير يرى صفحة «إشراف السكرتارية» مع اسم النائب وآخر مراجعة. لا يشترط اطلاع السكرتير لمواصلة التنفيذ.
5. اضغط على إشعار تحديث فتُفتح نافذة التقييم أو التحديث مباشرة بحسب صلاحية المستخدم ونوع الإشعار. أما فتح المشروع العادي فيتيح رمز ⓘ لسجل المحطة.
6. عند طلب تحديث من المسؤول يظهر الإشعار له؛ لا يمكن تكرار الطلب حتى يرد بتحديث جديد.
7. افتح القائمة الجانبية وأغلقها في الكمبيوتر والهاتف. تأكد أن نافذة الإشعارات لا تختفي خلفها وأن بوابة العضو لا تتكرر داخل القائمة.
8. اختبر شاشة الرئيسية بحساب سكرتير، نائب متابع، مسؤول مشروع، وGS؛ يجب أن تختلف الأعمال المطلوب اتخاذها حسب الصلاحية.

## ما الذي لم تثبته الفحوص المحلية؟

نجح فحص TypeScript والفحوص الثابتة. لم يكتمل `vite build` في بيئة Linux المستخدمة للتجميع بسبب غياب ملف Rollup native من الحزم المحلية. ولم تختبر هذه الحزمة على قاعدة بيانات الرابطة الحية أو بواسطة اختبارات متصفح تلقائية متعددة الحسابات. **نجاح GitHub Actions والاختبارات الحية شرط للإطلاق**.

### ملاحظة دقة مهمة

«آخر تحديث لم يُقيّم» يعني عدم وجود تقييم **مسجل على نسخة التحديث نفسها**. لا يعني أن النائب لم يتابع إطلاقًا خارج الموقع. كذلك التقييم ليس موافقة لازمة ليستمر المسؤول في المحطة التالية.
